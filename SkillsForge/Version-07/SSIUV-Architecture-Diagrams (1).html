SSIUV
Sales Services Intelligent Unified Validations
Skills-based test validation platform for end-to-end integration testing across digital sales services.
WHAT THIS IS
A platform where QA engineers define test scenarios as SKILL.md files and business users execute them on-demand. The AI reads the skill, calls the APIs, passes data between steps, checks results, and returns a pass/fail report. Business users provide input criteria through a form or Excel file. They do not need to know API endpoints, authentication, or data formats.
HOW IT WORKS
1
QA engineer writes a SKILL.md file defining the test scenario — inputs needed, APIs to call, data to pass between steps, what to assert.
2
Skill is uploaded to the platform. Platform validates it and stores it in the skill library.
3
Business user selects the skill, fills in criteria (model year, make, country, channels, etc.) via a dynamic form or Excel upload.
4
AI reads the SKILL.md, authenticates with each API via JWT, executes the workflow steps, evaluates assertions, returns results.
5
Results show pass/fail per step with details. Failed steps include error information and response data for investigation.
KEY DESIGN DECISIONS
SKILL.md is the contract.
One file defines everything — inputs, workflow, assertions. Both humans and AI read it.
Credentials are centralized.
Service Registry holds all API auth. Skills reference services by name. No tokens in skill files.
Two execution paths.
AI handles ~95% of skills dynamically. Critical skills that need 100% determinism get implemented as Temporal workflows using the same SKILL.md as the spec.
Optional scripts.
Skills can include .sh, .py, or .js files for logic too complex for AI to handle reliably (EventHub listeners, custom validators). Most skills need only the SKILL.md.
Async execution.
Runs can take minutes (batch, EventHub waits). Users don't need to keep the page open. Results are stored and searchable.

What Are Claude Skills?
How the Anthropic SKILL.md pattern works and how SSIUV applies it to test validation.
THE SKILL.MD PATTERN
WHAT IS A SKILL?
A Skill is a markdown file (SKILL.md) that gives an AI model instructions on how to accomplish a specific task. Anthropic introduced this pattern for Claude — the AI reads the file at runtime and follows the instructions to perform work.

The file is plain text. It is readable by both humans and AI. It describes what to do, what inputs are needed, and what outputs to produce. It can optionally be packaged with supporting code files (.sh, .py, .js) for operations the AI should delegate to scripts.
HOW DOES THE AI USE IT?
At execution time, the AI model (Claude) receives the SKILL.md content as context. It reads the instructions, understands the task, and executes it — making API calls, processing data, evaluating conditions, and generating output.

The AI does not need pre-compiled code or a fixed workflow engine. It interprets the SKILL.md dynamically. This means new skills can be created by writing a markdown file — no code deployment required. The skill author writes instructions; the AI follows them.
HOW SKILLFORGE APPLIES THIS PATTERN
SSIUV extends the SKILL.md pattern with structured sections that the platform can parse and act on. A standard Anthropic skill is free-form instructions. A SSIUV skill adds machine-readable sections for input collection (UICriteria), workflow steps (WorkflowDefinition), and output formatting (OutputDefinition).
Standard Anthropic SKILL.md
--- name: example-skill description: Does a specific task --- # Instructions When the user asks you to do X, follow these steps: 1. Do this first 2. Then do this 3. Check the result
SSIUV SKILL.md (extended)
--- name: test-gmc-offers version: 1.0 execution_mode: ai --- <UICriteria> <Type>HTML</Type> <Fields>{ "make": {...} }</Fields> </UICriteria> <WorkflowDefinition> <Tasks> <Task id="1" name="Create Vehicle"> Service: TDI Inputs: make={make} Capture: vin, account_number Assert: vin is not null </Task> </Tasks> </WorkflowDefinition>
SKILL.MD SECTIONS — WHAT EACH ONE DOES
Metadata
YAML front matter. Contains the skill name, version, author, tags, and execution mode (ai or workflow). The platform uses this for the skill library — search, filtering, display.
UICriteria
Tells the platform what inputs to collect from the user. Defines whether to show an HTML form, accept an Excel file, or both. For HTML, specifies each field: name, type (text, select, multi-select, checkbox), options, defaults, required flag.
WorkflowDefinition
Ordered list of Tasks. Each task names a service and operation from the Service Registry, maps inputs (from user criteria or prior task outputs using {Task1.vin} notation), declares what to capture from the response, and defines assertions to evaluate.
OutputDefinition
Optional. Tells the AI how to format the results report — what summary table to show, which fields to highlight, how to group results. Written in plain language; the AI interprets it.
Scripts
Optional. Maps specific tasks to .sh, .py, or .js files included in the skill package. Used for logic that's too complex or sensitive for AI to handle dynamically — EventHub listeners, custom data transformations, external validations.
Workflow Constructs
Tasks support: loops (for each channel in {channels}), conditionals (Assert if {validate_tax}:), optional tasks, and wait/poll with configurable timeout and interval.

Sales MCP Servers
Extending existing Spring Boot microservices as Model Context Protocol (MCP) servers using Spring AI, and how this connects to SSIUV.
WHAT ARE MCP SERVERS AND WHY THEY MATTER HERE
WHAT IS MCP?
Model Context Protocol (MCP) is an open standard that lets AI models directly discover and call tools exposed by servers. Instead of the AI needing a Swagger spec and custom HTTP code to call an API, an MCP server advertises its capabilities as typed tools. The AI model sees them natively and can invoke them directly.

Spring AI provides spring-ai-mcp-server — an annotation-driven way to expose any existing Spring Boot service as an MCP server. Add @Tool annotations to your service methods and your existing REST API becomes AI-callable.
HOW THIS HELPS SKILLFORGE
Today, the AI Execution Engine calls APIs via REST using the Service Registry (URL + JWT + Swagger). This works, but the AI must interpret Swagger specs and construct HTTP requests.

With MCP servers, the AI sees typed tools directly: createVehicle(make, model, year) instead of parsing POST /api/v1/vehicles with a JSON body. This means fewer AI interpretation errors, faster execution, and the AI can discover available operations without needing Swagger specs in the registry.

HOW MCP CHANGES THE SKILLFORGE ARCHITECTURE
BEFORE — REST + SERVICE REGISTRY
AI reads Swagger spec from Service Registry
AI constructs HTTP request body from SKILL.md input mappings
AI manually extracts fields from JSON response using JSONPath
AI manages JWT auth token lifecycle
Swagger specs must be uploaded and kept in sync
Failure mode: AI misinterprets request format, wrong field mapping
→
AFTER — MCP SERVERS
AI sees typed tools: createQuote(offerId, vin)
Parameters are typed — no body construction needed
Return types are typed — no JSONPath extraction
Auth handled by MCP server internally (Spring Security)
Tool schema auto-generated from Java code — always in sync
Fewer AI errors: typed invocation = no format guessing
ADDING MCP TO AN EXISTING SPRING BOOT SERVICE — WHAT IT TAKES
1. Add dependency (pom.xml)
<dependency> <groupId>org.springframework.ai</groupId> <artifactId>spring-ai-mcp-server-spring-boot-starter</artifactId> </dependency>
2. Annotate existing service methods
@Service public class OfferService { @Tool("Get offers for account, VIN, channel, and sales segment") public List<Offer> getOffers( String account, String vin, String channel, String salesSegment) { // existing business logic — no changes return offerRepository.getOffers(account, vin, channel, salesSegment); } }
No changes to existing business logic. No new REST endpoints. The @Tool annotation exposes the method as an MCP tool. Spring AI auto-generates the tool schema from the method signature, parameter names, and the description string. The existing REST API continues to work alongside MCP.
