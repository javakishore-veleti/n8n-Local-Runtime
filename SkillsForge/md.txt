Excellent question — this is the real engineering problem. The UI is the easy part. The hard part is exactly what you're asking: how does the system actually connect to, authenticate with, and orchestrate across multiple business applications? Let me break down the architecture thinking.
 
The Core Challenge
When a user types "Verify new customer in Salesforce syncs to SAP," the system needs to know: where is Salesforce? How do I authenticate? Which API endpoint do I call? What does "customer" mean in Salesforce's data model? And then the same questions for SAP. And then how to chain them together.
There are roughly 4 layers to solve this:
 
Layer 1 — Connector Registry (the "how do I talk to each system" problem)
You need a configuration layer where each integrated system is pre-registered with its connection details: base URL, auth type (OAuth2 for Salesforce, JWT for SAP, API key for others), endpoint catalog, and data model mappings. Think of it like a plugin system. You wouldn't dynamically discover APIs at runtime — you'd have pre-built connectors for each system (similar to what MuleSoft, Workato, or Boomi do).
The question is: do you build these connectors, use an existing integration platform, or expect customers to configure them?
Layer 2 — Authentication & Credential Vault
Each system authenticates differently. Salesforce uses OAuth2 with refresh tokens. SAP might use JWT or basic auth with certificates. You'd need a secure credential vault (something like HashiCorp Vault or AWS Secrets Manager) that stores and manages tokens per environment (dev/staging/prod). The orchestration engine fetches fresh tokens before each test run — users never see or manage tokens directly.
Layer 3 — The AI Translation Layer (NL → Executable Plan)
This is where it gets interesting. The AI doesn't just generate "test steps" as text — it needs to generate a structured execution plan that maps to real API calls. For this to work, the AI needs context about what connectors are available, what operations each system supports, and what the data models look like. You'd feed this as system context to the LLM.
So the prompt isn't just the user's query — it's the user's query plus a schema of available systems, their operations, and their data fields.
Layer 4 — Orchestration Engine
This is the runtime that takes the structured plan and executes it. It handles sequencing (step 1 before step 2), wait conditions ("wait up to 5 minutes for sync"), assertions (check field X equals Y), parallel checks, error handling, retries, and rollback/cleanup of test data.

Great choice. Catalog + Playbook is the most enterprise-friendly path — it's predictable, auditable, and you can ship incrementally. Let me think through how this actually works end to end.
 
The Big Idea in One Sentence
You build a library of pre-defined, tested, atomic operations for each system. The AI's only job is to understand what the user wants and assemble the right atoms in the right order with the right parameters.
 
Let's think about the Catalog first.
An atomic operation is the smallest testable unit. For example:
For Salesforce, that might be "query a record by field," "check field value equals X," "verify record was created after timestamp T." For SAP, it could be "check material document exists," "verify purchase order status," "confirm inventory quantity." For an API, it's "call GET endpoint, assert status 200, assert response body contains X."
Each atom in the catalog would have a fixed shape — it knows which system it talks to, what credentials it needs, what parameters the user (or AI) must provide, and what a "pass" looks like. Think of it like a function signature. The atom for "Salesforce: check record exists" might need: object type, field name, field value, and expected result.
The key question here is granularity. Too granular and you need hundreds of atoms to cover basic scenarios. Too coarse and you lose flexibility. Where do you think the right level is? For example, is "verify customer syncs from Salesforce to SAP" one atom or three (check Salesforce record → wait → check SAP record)?
 
Now the Playbook layer.
The AI takes the user's natural language and produces an ordered sequence of catalog atoms with filled-in parameters. So when someone says "verify new customer syncs to SAP and triggers welcome email," the AI output isn't English prose — it's a structured sequence like:
•	Atom 1: Salesforce → query Contact where Email = X → expect: exists
•	Atom 2: Wait → 5 minutes
•	Atom 3: SAP → query Business Partner where email = X → expect: exists
•	Atom 4: Email System → check sent mail where recipient = X, template = "welcome" → expect: delivered
The user sees this as a readable test plan. Under the hood, it's a machine-executable sequence.
 
This raises three design questions I think we need to wrestle with:
First — parameter resolution. When the AI builds the playbook, some parameters are obvious from context ("Salesforce," "SAP"). But others are ambiguous. What does "customer" mean? Is it a Contact, Account, or Lead in Salesforce? Does the AI guess, ask the user, or do you pre-configure business glossary mappings (e.g., "customer" = Salesforce Account + SAP Business Partner)?
Second — the wait/dependency problem. Integration tests aren't instant. Syncs take time. Events are asynchronous. How does the orchestrator handle "wait until X happens or timeout after Y minutes"? This is where most integration testing tools get complicated. You need polling, retry logic, timeout handling — and the user needs to see this happening in real time.
Third — test data. Does the platform create test data (e.g., insert a new customer to test the sync), or does it only validate existing state? Creating test data is powerful but dangerous — you're writing to systems. Validating existing state is safer but less useful for true end-to-end testing.
 
What's your thinking on these three? Especially the test data question — that's often where enterprise buyers get nervous or excited depending on their maturity.

Or is it just "did it return something reasonable and not null/zero?" — a sanity check rather than a precision check.

That's a brilliant fallback strategy. Same SKILL.md, two execution paths.
 
The 95% path: AI reads the SKILL.md, interprets it, orchestrates dynamically. Fast to create, flexible, good enough for most testing scenarios. Business users and QA engineers author skills quickly and run them.

What's beautiful about this is the lifecycle.
A skill starts as a SKILL.md. Business users run it via AI execution. It works well. Over time, that skill becomes critical — maybe it's part of a release gate or a compliance check. At that point, a developer "hardens" it into a Temporal workflow. The SKILL.md doesn't change. The execution engine underneath just switches from AI-interpreted to deterministic.
From the business user's perspective, nothing changes. Same skill in the dropdown, same criteria form, same results page. They don't know or care whether the AI or a Temporal workflow ran it. The platform just routes to the right engine.
 
This also gives you a natural product maturity story.
Launch with AI execution only. It covers most use cases immediately. Then as customers identify which skills are mission-critical and need hardening, you offer the Temporal path as a premium capability or a professional services engagement. "We'll productionize your most important skills."
And Temporal is a great choice specifically because it handles exactly the things AI might struggle with — long-running workflows, retries with backoff, wait conditions, fan-out/fan-in, failure recovery, and auditability. It's built for durable orchestration.
